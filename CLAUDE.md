# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

造场 (Zaochang) — a creator community + open product ecosystem. Community features (feed, circles, collections, studio, wallet), a "product galaxy" showcase, invite-gated GitHub login, a full OAuth 2.1/OIDC provider for third-party apps, and an internal ledger currency called 果子 (fruit). Runs on Cloudflare Workers (D1 + R2); the Alibaba box is now scanner-only.

## Commands

Requires Node `>=22.13.0` (tests use `node:sqlite` and `--experimental-strip-types`).

```bash
npm ci                          # install
npm run dev                     # vinext dev server (local D1/R2 via @cloudflare/vite-plugin)
npm run build                   # -> dist/server/index.js (Worker) + dist/client (assets)
npm test                        # builds (vinext), runs the full suite(测试数以 node:test 输出为准,不在此固定数字)
npm run lint                    # eslint
npx tsc --noEmit                # typecheck (root; hyperknow-spa 有独立 tsc,由 spa-typecheck 测试门禁强制)
npm run db:generate             # should output "No schema changes"; new SQL = drift (see below)
npm audit --omit=dev --audit-level=high --prefer-online   # use --prefer-online: stale cache gives false HIGH findings
git diff --check                # whitespace gate (also enforced in CI)
```

Run a single test (build once first — the harness needs `dist/`, then it still spins up the preview server):

```bash
npm run build
node --experimental-strip-types --test --test-name-pattern="<test name substring>" tests/rendered-html.test.mjs
```

## Architecture

**Runtime/build split.** This is Next.js 16 App Router source, but it is **not** built or run with the Next/Node toolchain. It builds with **vinext** (Vite + `@cloudflare/vite-plugin`) and runs on **Cloudflare Workers**. The Worker entry is `worker/index.ts`, which wraps `vinext/server/app-router-entry` and adds, per request: OIDC discovery (`/.well-known/openid-configuration`), image optimization (`/_vinext/image` via the `IMAGES` binding), an 11 MiB request-body guard, and security headers whose CSP **varies by path** (embedded apps under `/product-apps/` get `X-Frame-Options: SAMEORIGIN`; `/api/auth/github/start` gets a special locked-down CSP from `GITHUB_CONNECTION_CSP`). CSP and origin-resolution helpers live in `app/lib/` (`security-policy.ts`, `public-origin.ts`); sign-in is additionally guarded by Cloudflare Turnstile (`app/api/_lib/turnstile.ts`).

**Bindings access — the one pattern to know.** Route handlers do **not** receive `env` as a parameter. D1/R2 are read via the module-scope `env` from `cloudflare:workers`:

```ts
import { env } from "cloudflare:workers";          // app/api/_lib/community.ts
export function database() { return env.DB; }       // D1 binding "DB"
// R2 binding is "UPLOADS"
```

All DB access in routes goes through `database()` in `app/api/_lib/community.ts`. Bindings are declared in `.openai/hosting.json` (`d1:"DB"`, `r2:"UPLOADS"`) for local dev, and in `wrangler.prod.jsonc` for production.

**Auth paths** (keep their credentials/redirects separate):
- **GitHub login** (造场 as OAuth *client*): `app/api/auth/[provider]/{start,callback}`, session table `auth_sessions` (token stored SHA-256 only), cookies HttpOnly/SameSite=Lax. `start` returns a same-origin "connection page" that probes GitHub reachability before redirecting (network resilience), and accepts invite codes via **POST only** (never GET — invite codes must not enter URLs/logs). First-time GitHub identity requires an invitation code consumed atomically by a DB trigger.
- **Email verification-code login** (no external IdP): `app/api/auth/email/{request,verify}` + `app/signin/email-form.tsx`. A 6-digit code (rejection-sampled, SHA-256-hashed at rest, 10-min TTL, 5-attempt lockout, atomic single consume via `meta.changes`) is emailed from `zaochang@aetherstudio.top`. Transport resolves at runtime in `app/api/_lib/email-send.ts`: `EMAIL_SEND_*` vars (REST override, **test-harness only**) → `EMAIL` `send_email` binding (prod, wrangler configs) → neither ⇒ inert 503 `email_not_configured`, checked **before any DB write** so empty-DB environments stay testable. Existing `members.email` logs in with no invite; a new address must carry an invitation code and runs the same atomic batch as OAuth (provider `'email'`), with the same SQLite trigger gate. `hashInvitationCode` normalizes entry before hashing (strips whitespace incl. full-width, maps full-width→half-width, uppercases) — transcription tolerance for hand-typed `ZC-…` codes, not a gate weakening (the generated plaintext is already uppercase half-width, so normalization is identity there and every accepted input still must hash-match a real code). Rate limits: per-IP 10/h + per-address 3/15min; Turnstile is checked on **every** code request when configured (each call sends real email — unlike GitHub start, which only gates invite submissions). Codes live in `email_login_codes` (migration `0018`, which also widens the three provider CHECKs to `'email'`; note it drops + recreates the invitation triggers — see comments in the SQL).
- **Account applications → emailed invitation codes** (`/apply` + admin 「账户申请」 section): public `POST /api/account-applications` (same-origin, Turnstile when configured, per-IP 5/h + per-address 3/day + global 200/day) stores a row in `account_applications` (migration `0042`) and answers a uniform 202 for new / duplicate-pending / already-member — no mail is ever sent on submission. Admin approve (`PATCH /api/admin/account-applications`, also in `AGENT_ADMIN_CAPABILITIES`; the direct-invite `POST` is human-only) runs one `db.batch` that inserts a single-use `invitation_codes` row + flips the application to approved + audits, every statement conditioned on the current state (SQL shared in `account-application-sql.ts`, race-tested on node:sqlite in `tests/account-applications.test.mjs`), then mails the plaintext via the `EMAIL` binding using the pure template `invite-mail.ts` (admin preview renders the same function with a placeholder code). Plaintext appears only in that email — never in responses, audit, or any link. Mail failure revokes the fresh code (`mail_status=failed`); "重发" revokes the unused old code and issues a new one. Codes are bearer (not bound to the applicant's email). DB CHECKs: approved ⇔ invitation attached; mail status only on approved; one pending row per email (partial unique index).
- **Admin-provisioned accounts + first-sign-in onboarding** (migration `0043`): `POST /api/admin/accounts` (human admin session only — `guardWrite "admin"`, not in any agent capability table) creates `members` (+ wallet, + `admin_provisioned_accounts` row, + audit, closes a pending application for the same email) **without an invitation code** — the invite gate lives on the `oauth_accounts` insert trigger, and provisioning never writes `oauth_accounts`; the person signs in by email code through the "existing member" branch. The notice mail (`accountProvisionedEmail`) carries no credential, so a mail failure keeps the account (`mail_status=failed`, `PATCH` `resend_notice`). Every new registration (invite via email/GitHub, or provisioning) sets `members.onboarding_required=1`; dev-login, `ensureMember` and pre-0043 members stay 0. `worker/onboarding-gate.ts`: for **document navigations only** (`sec-fetch-mode: navigate`, or `Accept: text/html` when the header is absent) with a session cookie on non-exempt paths (`/welcome`, `/signin*`, `/signout`, `/apply`, `/api/*`, static files… exempt), the worker reads the flag via `sessionUserFromTokenValue` (same row, no extra query) and 302s to `/welcome?return_to=`; `/lattice` gets the same check. It is a UX gate, not a security boundary (API/RSC requests are not blocked). `/welcome` → `POST /api/onboarding` sets a **unique, immutable username** (`^[a-z][a-z0-9_]{2,19}$`, NFKC+lowercase, reserved list in `member-identity-rules.ts`) + nickname (2–20 code points, may repeat) + optional bio/location/website, then clears the flag. `members.display_name_custom=1` once a person sets a nickname → GitHub login stops overwriting `display_name` (`SYNC_PROVIDER_DISPLAY_NAME_SQL`). Profile edit: nickname editable, username claimable once by legacy members (`/api/profile/identity`). Both identity writes require `authVia === "session"`. DB triggers enforce username format, immutability, and "onboarding can only end with a username". Note for tests: Node's global `fetch` (undici) rewrites `sec-fetch-mode` to `cors`, so navigation tests must use `node:http` (see suite 21).
- **Passkey (WebAuthn) login** (no external IdP, no secrets): `app/api/auth/passkey/{register,login}/*` + `app/signin/passkey-button.tsx` + `app/profile/edit/passkey-manager.tsx`. Passkeys are **add-on credentials for existing members only** (`/profile/edit`, `requireMember`) — they never create accounts, so the invitation-trigger batch is not involved. Login is discoverable/usernameless (empty `allowCredentials`; email narrows it without leaking existence). Challenges are **consumed server-side** in `webauthn_challenges` (SHA-256 at rest, `purpose` isolates register/login, conditional UPDATE + `meta.changes` — the cookie alone has no replay defense, and counter checks can't save counter=0 synced credentials). Credentials live in `webauthn_credentials` (`user_handle` = stable per-member random handle, no PII; COSE public key; counter/deviceType/backedUp — synced credentials may keep counter 0, clone detection follows deviceType). Both tables arrived in migration `0028`, which also rebuilds `auth_sessions` to widen its provider CHECK with `'passkey'` (SQLite CHECK change = full table rebuild, same pattern as `0018`). RP ID + expected origins derive **only** from `PUBLIC_APP_ORIGIN` (`webauthnRpConfig`; a `www.` variant is allowed for non-IP multi-label hosts — passkeys registered on apex work on www). Verification via `@simplewebauthn/server` v14 (WebCrypto/noble, Workers-safe); `attestationType: 'none'`. Sessions issue through the same `createOAuthSession(provider 'passkey')` pipeline — full parity with GitHub/email, SSO//lattice/OIDC untouched. Login endpoints are open but rate-limited per-IP 30/15min; errors are uniformly `passkey_invalid` (no credential-existence oracle). No Turnstile (the ceremony itself is possession+biometric). Fixture-driven end-to-end tests (real ES256 assertions, minimal CBOR encoder) live in `tests/suites/12-passkey.tests.mjs`; contract pins in `tests/passkey-core.test.mjs`.
- **造场 as OIDC *provider***: `app/api/oauth/*` + `app/oauth/authorize/` + `app/oauth/payment/[id]/`. Authorization Code + PKCE S256, ES256 ID tokens (pairwise sub), rotating refresh tokens with family-wide revocation on replay. Third-party `fruit:pay`/`fruit:refund` require admin client approval and **per-payment user confirmation** on a造场 page. Core logic in `app/api/_lib/oauth-provider.ts` and `app/api/_lib/external-fruit.ts`.
- **Agent service account** (machine identity, parallel to the human paths): a single long-lived bearer token (`ZAOCHANG_AGENT_TOKEN`) gates a hardcoded write-capability table (`AGENT_WRITE_CAPABILITIES` in `app/api/_lib/agent-auth.ts`). It is enforced as a **fail-closed chokepoint at the worker entry** (`worker/index.ts`, before any route): with the token set, agent GETs pass but every non-GET must match the table exactly or the worker returns 403 *before* the route runs. The table is deliberately tiny (currently `POST/PATCH /api/docs`, `POST /api/products`) — DELETE / finance / uploads / admin / social are never in it. Token unset → this path is inert (zero behavior change). Agent writes run the same business code, so all SQLite-trigger invariants still apply.
- **Personal user API key + MCP** (phase 1): signed-in members create/list/revoke keys through `/api/api-keys`; these routes require a Cookie session and check `authVia === "session"`. Key plaintext is `zc_` + 32 random bytes in base64url, returned once; D1 stores only the SHA-256 hash and display prefix. Keys expire after exactly 30/90/365 days, are capped at five active keys per member, and creation is rate-limited. `worker/index.ts` checks every request method for a `Bearer zc_...` credential before routing; only exact `POST /api/mcp` is in the separate `USER_KEY_CAPABILITIES` table (`app/api/_lib/user-api-key.ts`). Unknown, expired, or revoked `zc_` values return 401 without Cookie fallback. MCP accepts Bearer only, advertises RFC 9728 resource metadata on 401, checks any supplied Origin against the configured public origin, and rate-limits each key. The resolved identity has `authVia: "api_key"`, `isAdmin/isFounder/isAgent === false` even for a whitelisted owner; key management remains session-only. Project tools use the shared create/update functions, existing per-member submission limit, ownership checks, and review triggers. Cover uploads remain private and must pass `storeScannedUpload`; scanner failures never create a clean cover.
- **MCP external demo notice**: `create_product` and `update_product` return additive `warnings` when a non-empty `demo_url` is submitted. External demo links cannot currently pass review because experience content must not be replaceable in place; until static hosting is available, leave the field empty and present the project with its cover and description. An omitted or whitespace-only `demo_url` returns `warnings: []`.
- **MCP OAuth (phase 2)**: Claude Code/Codex dynamically register public clients at `/api/oauth/register` and use Authorization Code + PKCE S256 + user consent; `mcp:projects` is the only MCP capability and is not a 果子 write scope. MCP access/refresh tokens bind to the exact resource `<origin>/api/mcp`; `/api/mcp` accepts only `zca_` tokens with that resource and `mcp:projects`, while general `requireBearer` rejects every non-null resource. OAuth tokens are parsed only inside `/api/mcp` and carry `authVia: "oauth"`, `clientId`, and false admin/founder/agent flags; they never enter `getChatGPTUser`. Dynamic clients have no member owner/list row, are constrained by DB CHECK/trigger guards to `public`, `unverified`, no write approval, and `mcp:projects` with optional `openid`. Production loopback decision (user-approved this turn): only dynamic-client authorization redirects may use `http://localhost`, `http://127.0.0.1`, or `http://[::1]`; the registered URI including port must match exactly. Developer-registered redirects and external fruit payment return URIs still reject loopback in production. DCR is IP-limited to 10/hour, limited to 2,000 recent never-authorized clients, rejects platform-impersonating names (checked on the primary name before a trailing parenthetical — clients send e.g. `Claude Code (zaochang)` where the parenthetical is the user's local server name) and non-MCP scopes (an empty/absent scope defaults to `mcp:projects`, at registration and at authorization for dynamic clients), and is excluded from the admin OAuth review queue; `/.well-known/oauth-authorization-server` advertises only `mcp:projects` in `scopes_supported` because Codex CLI registers exactly that list (the full scope list stays in OIDC discovery); dynamic consent screens always identify the unverified/self-claimed client and full callback address. Each member has at most 10 active dynamic-client consents; consent revocation invalidates access and refresh tokens. `initialize` answers an unsupported client protocol version with the newest supported one (`2025-06-18`) instead of an error, and later requests with an unsupported `MCP-Protocol-Version` header get 400. MCP limits are per API key 60/minute or per OAuth client+member 60/minute, plus a shared per-member 120/minute bucket; project submission and cover upload limits reuse the same per-member keys as web routes. Each MCP write tool call records credential kind/id, tool, product id, result code, and timestamp without request/file contents; purge removes unconsented dynamic clients after 7 days and audit/API key records per their 90-day retention rules.
- **First-party MCP client CLI (`cli/zc.mjs`, zero-dep Node ≥22)**: terminal access to the same `/api/mcp` surface as Claude Code/Codex. Both credential tracks implemented: OAuth (DCR + PKCE S256 + `127.0.0.1` loopback callback on an ephemeral port registered exactly, rotating refresh persisted to disk on every refresh) and personal `zc_` API keys (`login --api-key` or `ZC_API_KEY`). Commands: `login`/`logout` (revokes the token family)/`whoami`/`ping`/`tools list`/`call` (`--arg k=v` values JSON-parsed with string fallback)/`host upload <product_id> <bundle.zip>` (begin_hosting_upload + one-time PUT + get_hosting_status). Credentials live in `~/.zaochang/zc-cli.json` (0600; `ZC_CLI_CONFIG`/`--config` override); `--origin` must match the logged-in origin or the CLI refuses. Refresh-token rotation semantics are load-bearing: a replayed refresh token revokes the whole family, so `oauthTokenProvider` writes the new pair synchronously before any further use. Tests: `tests/zc-cli.test.mjs` (fake-origin HTTP server replicating the server contract; child-process runs must use async `spawn` because `spawnSync` blocks the in-process fake server → parent/child deadlock). Run via `npm run cli -- …`; docs in `cli/README.md`.
- Identity also has a legacy header path (`getChatGPTUser()`, `oai-authenticated-user-*`). These headers are trusted **only** when `APP_ENV` is exactly `development` or `test` (fail-closed allowlist, same gate as dev-login); production/staging/unset/typo'd `APP_ENV` always rejects. The former `TRUST_OAI_IDENTITY_HEADERS` escape hatch was removed (2026-10 audit).
- **Local dev login** (simulated, for local/CI only): `GET /api/auth/dev-login[?email=&return_to=]` issues a real `zaochang_session` without GitHub, via the same `createOAuthSession`/`setAuthCookies` pipeline as the callback. Double fail-closed gate in `app/api/_lib/dev-login-gate.ts`: `APP_ENV=production` returns 404 unconditionally (even with the flag set), and non-production still requires **both** `APP_ENV` ∈ {development, test} **and** `LOCAL_DEV_LOGIN=1` (unset/typo'd APP_ENV stays closed). Also rejects `sec-fetch-site: cross-site` (login-CSRF guard) and open-redirect `return_to`. Enable locally with `wrangler dev --var APP_ENV:development --var LOCAL_DEV_LOGIN:1`, then visit the URL in any browser. Never set `LOCAL_DEV_LOGIN` in production secrets.
- `app/oauth-session.ts` is the shared session/cookie/invite core.
- **Access control is modularized**: `app/api/_lib/access-control.ts` is the single import surface for authorization decisions — declarative `authorize({ member, roles })` (kept deliberately as the registration surface for new routes though present routes use the imperative helpers — 2026-10 audit A10 decision), imperative `requireRole`/`requireAdmin`/`requireFounder`/`requireDocEditor`, and the generic content gate `canViewContent` (docs' `canViewDoc` delegates to it; any new content type can adopt the same `public|members|private` semantics in one call). Role whitelists stay in `admin.ts` (`isAdminEmail`/`isFounderEmail`), and `access-control.ts` evaluates them only for `authVia: "session"` or `"legacy"` identities through the zero-import `role-eligibility.ts` guard; every other or unknown identity source is ineligible for email-based roles. Hyperknow checks paid tier mappings first; without a paid mapping, a founder-email identity from another source gets 403 before shared credits or a lease are read or changed. Enabling gating on a new route or content type is a code-level declaration — no visible UI entry is created for it.

**Permissions are two independent flags.** `member.isAdmin` (from `ZAOCHANG_ADMIN_EMAILS` whitelist; empty = nobody) and `member.isFounder` (from `ZAOCHANG_FOUNDER_EMAIL`, must be a single value) neither implies the other. `/admin` and `/founder` are separately gated (`requireAdmin` / `requireFounder` in `app/api/_lib/admin.ts`).

**Data model & money invariants.** Drizzle ORM over D1/SQLite. Schema: `db/schema.ts`; migrations: `drizzle/0000..` (forward-only — never reverse-delete columns, triggers, or ledger rows). 果子 is a **double-entry, immutable** ledger (`fruitOperations` + `fruitEntries`); materialized wallet balances must equal ledger aggregation or transactions fail with `wallet_ledger_mismatch` and the wallet goes to `review`. Critical invariants (product-review gating, refund windows, like-reward anti-abuse, invite atomic redemption, OAuth account creation) are enforced by **SQLite triggers** in the migrations, not just app code — so they hold even for direct D1 writes.

**Static project hosting (StepFun Page).** Invited members (admin-granted via `hosting_grants`, `/api/admin/hosting-grants`) can host a static site: a zip goes through `inspectBundleZip` (`app/api/_lib/hosting-bundle.ts`, structure only, limits from `hosting-rules.json` aligned to ClamAV's archive limits), `storeScannedUpload` (zip is accepted only with `allowArchive` + purpose `hosting_bundle`), then one `db.batch` bumps `products.hosting_revision` (which re-hides an approved product via the material-change trigger), supersedes the old row and inserts `product_hostings`. The **deployer** (`deploy/hosting/`, runs on the Alibaba box, the only holder of the StepFun key) claims jobs from `/api/hosting-worker/*` (machine token `HOSTING_DEPLOYER_TOKEN`, `zch_` prefix, fail-closed 4-route gate at the worker entry, never an identity), re-validates the bundle (actual inflate + CRC + secret scan), deploys a **staged** version via the pinned `steppage` CLI, and reports back; after admin approval it promotes and reports `live`. Invariants live in SQLite triggers (see `deploy/hosting/CONTRACT.md`): approval of a hosted product requires a current-`hosting_revision` staged/live row (`hosting_not_staged`), `live` requires current approval, and public pages may only read the hosted URL through the view `product_hosted_urls` (also requires `desired='live'` and a `*.page.stepcloud.com` host; guarded by `tests/hosting-live-url-architecture.test.mjs`). External `demo_url` products still cannot be approved — hosted products keep `demo_url` empty. Agents use MCP `begin_hosting_upload` (one-time 15-minute PUT URL, never base64 in tool args) / `get_hosting_status` / `remove_hosting`. Ops: `CLOUDFLARE_RUNBOOK.md` §4b.

**Product review gate.** Every user-submitted product enters `pending_review`; only a current-version approved `productReviewDecisions` row makes it public. DB triggers block orders/likes/tips on non-approved products. Editing an approved product bumps `review_version` and re-hides it. The six built-in showcase apps under `/public/product-apps/` are trusted static code, **not** user uploads.

**Upload security pipeline.** Uploads go `uploaded_files.pending → ClamAV scan → clean|infected|error`. An object is readable only when the DB row **and** R2 object are both `clean` with matching SHA-256 and a valid scanner verdict for the same SHA-256 was received in HTTP 200. Missing scanner, timeout, malformed response, or non-busy failure remains fail-closed; upload-core marks the row `error` and deletes quarantine/formal R2 keys. The box runs one clamscan at a time with a FIFO queue of up to `SCANNER_QUEUE_MAX` (default 3) waiting requests, each waiting at most `SCANNER_QUEUE_WAIT_MS` (default 45000 ms); a full or expired queue returns 503 `scanner_busy` plus `Retry-After`, and `/health` exposes `busy` and `queued`. `server.requestTimeout` is 80 seconds for the whole request receive window, so the 45-second queue default leaves at most 35 seconds for the 10 MiB body. Worker retries only HTTP 503 with JSON `error: "scanner_busy"`, at most three additional attempts with 1/2/4-second backoff plus jitter, respecting `Retry-After` up to 15 seconds and a 110-second total budget; network errors, `scan_failed`, other statuses, SHA mismatch, and invalid verdicts do not retry. Every non-Hyperknow-image upload also passes the shared D1 `upload-global:all` bucket at 120/hour after file inspection and before an `uploaded_files` insert; existing per-member limits run first. Capacity refusal is 429 `upload_capacity_exceeded` with `Retry-After` and no upload row or R2 write. In production the scanner is the Alibaba box reached through a Cloudflare Tunnel at `scanner.aetherstudio.top` (see `CLOUDFLARE_RUNBOOK.md`).

**Reading AI proxy (书页「问 AI」).** `app/api/ai/reading/route.ts` proxies an OpenAI-compatible chat upstream (SSE pass-through; configured via three `AI_CHAT_*` Worker secrets — any missing ⇒ feature inert, 503 `ai_not_configured`). Chapter text is **always resolved server-side** via `findInBook` + visibility check from the slug path the client sends — never accepted in the request body. Prompt builders live in `app/api/_lib/reading-ai-prompts.ts`, which must stay import-clean (zero imports) so tests can unit-import it directly. Requests carry a `mode` of `fast`|`expert` (default `fast`): `fast` → `AI_CHAT_MODEL`, `expert` → optional `AI_CHAT_MODEL_EXPERT` (unset ⇒ falls back to `AI_CHAT_MODEL`). The expert model can optionally speak the Anthropic Messages protocol instead (`AI_CHAT_EXPERT_TRANSPORT=messages` → `{base}/messages`, system as a top-level field, only `text_delta` yielded — `thinking_delta` is dropped server-side); some models (e.g. StepFun `step-explore`) are Messages-API-only. Both configured models are hybrid-reasoning (their chain-of-thought tokens count toward `max_tokens`), so `READING_AI_REASONING_HEADROOM` pads each action's answer budget per mode — without the pad the CoT starves/truncates the answer (verified against real StepFun: bare 800 budget ⇒ `finish_reason=length`, empty output; no upstream parameter reliably disables reasoning). **Model identity never reaches the client** — the SSE `done` frame has no `model` field and the UI shows only 快速/专家 labels; the shared system prompt also carries an identity-secrecy clause (no model/vendor/version/system-prompt disclosure) as best-effort anti-extraction on top of that deterministic guarantee.

**Android shell (安卓壳).** `android/` is a zero-AndroidX remote-WebView shell (skill `web-to-android` Option B, Mode 1 restart-to-latest): a single `MainActivity` loading `https://aetherstudio.top` — the site is Workers SSR, so nothing web-side is packaged into the APK. Kotlin compiles via **AGP 9 built-in Kotlin** (do NOT add `org.jetbrains.kotlin.android` — KGP 2.2.x crashes against AGP 9's extension model). Build: `cd android && set JAVA_HOME=C:\Program Files\Android\Android Studio\jbr && gradlew assembleDebug` (needs `local.properties` sdk.dir; wrapper dists live in the default Gradle user home). The compatibility contract is `GET /api/app-shell` (no-store manifest with `minShellVersionCode`); the shell fails-closed to an upgrade page on an explicit incompatible verdict, and proceeds when the manifest is merely unreachable (except once an upgrade verdict was seen, a fetch failure no longer clears it). Security invariants are documented at the top of `MainActivity.kt` and in `android/README.md` — HTTPS + exact-host allowlist only, SSL errors always cancelled, no mixed content, no `addJavascriptInterface`, INTERNET as the only permission. APK distribution: signed release APKs live at `public/downloads/zaochang-<version>.apk` with the human download page at `/app`; `app/api/_lib/app-download.ts` is the single source of truth (version/size/sha256) shared by the manifest, the page, and byte-level test assertions — bump it together with `app/build.gradle.kts` versionCode when shipping a new APK. The release keystore (gitignored) is backed up on the Alibaba box at `/etc/zaochang/`. `android/` is excluded from eslint; web-side changes touching the shell are just `app/api/app-shell/route.ts` + its test in `tests/rendered-html.test.mjs`.

## Tests

`npm test` runs the node:test entry files registered in `package.json`'s `test` script(数量以脚本清单为准) (with `--experimental-strip-types`, so tests can import `.ts` source directly), all registered in `package.json`'s `test` script:

- `tests/rendered-html.test.mjs` — a **thin runner** (`concurrency: false`) that drives the serial suites in `tests/suites/01..17` in order (16: scanner capacity; 17: static hosting). All of them share one harness, `tests/harness/preview.mjs`: a **real Wrangler preview server** on port 4179 against a fresh local D1 (applies all migrations from empty), plus a fake upload scanner, fake AI chat upstream, and fake email transport — asserting real HTTP responses + DB field state against the live worker runtime and real triggers, not mocks. Suite 14 covers personal API keys, MCP scope, ownership, review state, and scanned covers. ## Deploy

Push to `main` → `.github/workflows/ci.yml` (`release-gates`: tsc, lint, disabled-test scan, `npm test`, `git diff --check`, migration-drift check, `npm audit --audit-level=high`) → on success `.github/workflows/deploy.yml` (triggered by ci's `workflow_run`) verifies all migrations are applied to prod D1 via `scripts/check-migrations.mjs` (ordered per-entry hash+created_at reconciliation, fail-closed), then runs `npx wrangler deploy --config wrangler.prod.jsonc` at the exact ci-approved SHA. Manual `workflow_dispatch` is **emergency-only**: it must still record the reason and owner, pin an exact SHA, run equivalent gates + migration check + smoke before opening paid writes — never treat it as a gates bypass. Local manual deploy: `npm run build && npx wrangler deploy --config wrangler.prod.jsonc`.

- **Do not rename** `wrangler.prod.jsonc` / `wrangler.staging.jsonc` to the standard `wrangler.jsonc`/`wrangler.toml`. The non-standard names are deliberate: they prevent `@cloudflare/vite-plugin` from auto-discovering the config and double-binding `DB`/`UPLOADS`, which breaks `npm test` with binding-name conflicts.
- Production secrets are sourced from the Alibaba box `/etc/zaochang/zaochang.env` — the only authoritative copy. (A `ZAOCHANG_AGENT_TOKEN` drift was found and fixed by rotation on 2026-10-02 — history and the sync discipline in `CLOUDFLARE_RUNBOOK.md` §2; every direct `wrangler secret put` must write the same value back to the box env.) The full per-environment list (12 required + 2 optional prod secrets, staging-only TURNSTILE_*, test-only EMAIL_SEND_*) is `CLOUDFLARE_RUNBOOK.md` §2 — that section is authoritative; see it for the pipe-injection pattern (never print values).
- Production app is on Cloudflare (D1 `zaochang-db`, R2 `zaochang-uploads`). The old Alibaba host deployment in `RELEASE_RUNBOOK.md` §8 is **deprecated** (box is ClamAV-only now). Local DNS for `aetherstudio.top` is unreliable (VPN hijack → `198.18.x.x`); always verify via the box `--resolve`-ing to the CF edge IP.

## Conventions & gotchas

- **Migration drift:** `npm run db:generate` must stay a no-op. If it emits SQL, `db/schema.ts`, the migration SQL, and `drizzle/meta/*.snapshot.json` are out of sync — reconcile before committing. CI checks this.
- **`PROJECT_STATUS.md`** is a chronological ledger but **can lag reality** (it has done before). Verify deploy state against live (`wrangler deployments list`, `gh run list`, or the box) rather than trusting it.
- Tests run on Windows; `git` may flag LF→CRLF conversions as warnings — those are not failures. `git diff --check` exit 0 is the gate.
- Authoritative docs: `CLOUDFLARE_RUNBOOK.md` (prod deploy + topology; §2 secrets; §6 视觉验收入场票), `LATTICE.md` (见界 module architecture/protocol diffs/prompt evolution), `OAUTH_SETUP.md` (OAuth/OIDC config), `RELEASE_RUNBOOK.md` (release gates + rollback), `PROJECT_STATUS.md` (chronological ledger), `db/schema.ts` (data model), `worker/index.ts` (request pipeline + security headers), `android/README.md` (安卓壳构建/发布/回滚).
- Path alias: `@/*` maps to the repo root (`tsconfig.json` paths); app code imports via `@/...`.
